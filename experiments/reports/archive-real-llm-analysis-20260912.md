# 历史 LLM 提交包真实模型对比分析

## 实验问题与口径

本实验在与既有离线对比相同的 6 个固定 50 节点合成种子、预算 100 条件下，直接加载 4 个历史 ZIP，并使用仓库已配置的真实 LLM 服务执行。每个 `(ZIP, 种子族)` 只运行一次，因此可以比较同种子上的真实 LLM 轨迹与强制失败回退轨迹，但不能估计模型重复采样方差，也不能把本地六种子均值换算为官方隐藏种子分数。

主要比较量是每个 ZIP 的真实 LLM 本地分数，以及相对同 ZIP、同种子 fallback 分数的配对差值。辅助检查包括完成状态、模型调用与接受数、fallback 数、传输错误、动作失败、剩余预算和动作构成。官方分数只作为独立外部结果并列展示；官方未公开种子和权重，不能据此计算逐种子配对差值。

原始结果由 `experiments/raw/archive-comparison-real-20260912/` 保存，完成后的机器可读汇总为 `experiments/reports/archive-score-comparison-real-20260912.json`。强制失败对照来自 `experiments/reports/archive-score-comparison-fallback-20260912.json`。

## 四个 ZIP 的 LLM 决策机制

| ZIP | 调用时点与上限 | 决策 JSON | LLM 可以改变的行为 | 稳定回退 |
|---|---|---|---|---|
| `starnet-public-greedy-llm-candidate-20260912.zip` | 每次扫描和干预前调用；50 节点赛段上限 120，策略内部上限 240，取较小值 | 严格单候选对象：`state_version`、`mode`、`candidate_id`、`reason_code`、`evidence_ids` | 从当前 Python 合法候选中选 1 项；扫描阶段可改扫描顺序，干预阶段可偏离确定性最高 ROI 项 | 当前状态下按 Python 排序选择合法候选 |
| `starnet-public-greedy-llm-audited-20260912.zip` | 与 candidate 相同 | 与 candidate 相同 | 与 candidate 相同；公开沟通/屏蔽 guard 显式关闭，双切边实验未启用 | 与 candidate 相同 |
| `v1-experiment-tools.zip` | 全量确定性扫描后，在批次规划时最多调用 3 次 | `mode`、`candidate_ids`、`reason`；最多 10 项 | 可改变候选批次的子集和顺序；三批之后按确定性排序 | 按优先级、ROI、成本和 ID 生成合法批次 |
| `v0-baseline-0904-1.zip` | 与 v1-experiment-tools 相同 | 与 v1-experiment-tools 相同 | 与 v1-experiment-tools 相同 | 与 v1-experiment-tools 相同 |

两个新包会把模型配额大量用于扫描。只要最终仍完成 50 个节点的全量扫描，扫描顺序本身不改变干预前的完整公开图；这些调用的直接终局贡献通常有限。真正可能改变分数的是扫描完成后的逐动作选择：模型可以选取一个合法但 ROI 较低的候选，随后环境返回又会改变下一轮候选集，因此一次偏离可能改变后续预算分配和整条轨迹。严格的状态版本、候选 ID 和证据校验会把过期、未知或无证据输出退回确定性选择。

两个旧包不让模型控制扫描，只让模型最多生成 3 个合法候选批次。模型可以省略高优先级候选、改变队列顺序，或选择不同动作类型；每个动作执行前仍会重新验证预算与冲突。因为每次调用最多选择 10 项，模型直接影响的动作范围最多为 30 项，配额耗尽后的选择恢复确定性。两个旧包的 Commander prompt 完全相同；`v1-experiment-tools` 增加了实验配置和安全步数开关，但默认值保持原阈值和 3 次调用，在既有六种子 fallback 结果中两包逐种子得分相同。

`candidate` 与 `audited` 的 Commander prompt 也相同。`audited` 增加了环境返回类型检查、可选 guard 和未启用的双切边实验；本 ZIP 配置明确关闭 guard，故预期候选决策面与 `candidate` 相同。由于这里只做每臂一次真实模型运行，如果两者出现差异，需先排查模型采样或服务波动，并核对实际候选和动作差异；不能仅凭单次实验归因于代码。

## 完整性检查与结果

24/24 个真实 LLM 会话均为 `completed`。合计 1,018 次真实模型调用、零传输错误、零动作失败。`candidate` 和 `audited` 各自的 491 次输出全部通过严格 schema、状态版本、候选和证据校验，两个包均记录 0 次 fallback。旧版控制器没有向 runner 暴露 `llm_accepted` 和 `llm_fallbacks`，对应字段为 `null`；它们的零传输错误不能证明 18 次输出都通过 schema。

两个新包在全部六类上有不同于 fallback 的动作哈希，但分数、动作类型计数和剩余预算逐项相同。这说明真实模型改变了部分动作或顺序，但没有改变终分；仅凭这些汇总指标不能证明终态完全相同。`candidate` 和 `audited` 之间则在六类上的动作哈希也完全相同，符合相同 prompt、相同候选决策面和关闭 guard 的源码预期。

## 结论边界

真实 LLM 在本矩阵中没有带来任何终局分增益：24 个配对差值全为 0。`candidate` 的官方成绩也与无 LLM 的 `v9` 完全相同，均为 `761.9467`，与本地“没有可观察分数贡献”的结果一致；由于官方样本未公开，这仍不是逐种子因果验证。当前证据不支持继续把调用次数或 prompt 微调当作突破 900 的主要方向。

下一步应优先改变 Python 生成的合法候选集合和预算分配，使候选之间存在经过独立种子验证的终局价值差异，再让 LLM 只处理少量、真正接近且不确定的候选。新包每局约 82 次调用，其中固定 50 次用于最终会完成的全量扫描，而本实验未观察到任何终局收益；保留逐扫描调用会增加延迟和服务波动暴露。候选策略先通过独立与 holdout 配对门禁，再用真实 LLM 重复运行以估计采样方差，最后才用官方评测检验是否向 900 推进。

本地无干预六种子均值为 `-76.9098`，说明本地绝对分包含强烈的场景难度差异；它不提供官方 `BaseAvg`，也不能用于推导官方增益。单个本地种子超过 900 或真实 LLM 六种子均值提高，均不等同于官方排行榜达到 900。

任何调用调度优化仍须满足赛方要求：每个智能体继承 CaseVO AgentBase，最终决策由 LLM 完成。此次保留历史 LLM-off 包仅用于对照，不构成按新规则重新提交这些包的建议。
