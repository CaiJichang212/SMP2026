【赛事紧急通报】关于禁止绕过 API 进行内存透视的规则补充
近日，经某参赛团队善意披露与组委会核查，发现在天池 Python 同进程评测环境下，存在通过反射机制（如 vars(env) 或直接访问 env.graph）越权读取沙盒底层隐藏内存状态的风险，此行为可无视精神力消耗，直接获取全知视角（约节省25精神力）

为维护赛事的绝对公平，组委会特此进行紧急系统热修复与规则补充：

1. 系统升级：天池评测机已实装 SecureEnvProxy 安全隔离网关，常规越权访问将被直接拦截并报错

2. 规则红线划定：组委会再次明确，任何试图绕过官方限定的 个合法 API，利用 Python 反射、垃圾回收（gc）等高阶机制强行透视评测机底层内存的操作，均被定义为【作弊行为】

3. 审校惩罚：在赛后的【人工代码审校】环节，我们将扫描选手的提交代码，一旦发现上述内存逃逸行为，将直接取消比赛资格与全部成绩（本次主动报告漏洞的团队不在此列，仅重置该违规分数）

Q:每一步决策都需要大模型参与吗？还是说大模型只在关键几个步做决策即可？
A:我们还是较鼓励大家调用大模型的哈，不过不需要每一步。只要整个干预过程中，核心决策有大模型真正参与推理即可。纯靠人工写死 if-else 规则下达指令会在代码审校时被判定违规

Q:你好，目前有以下一些问题

Q:请问一下，给的这个本地测试的环境api和提交测评的环境是完全一样的吗？最后采用的这个，还有战术干预里的固定的数值倾向修正，是与评测时一致吗？
A:环境机制是一致的。本地测试调用的 API 沙盒引擎，与天池线上评测机的底层代码是完全同源的；战术干预数值与测试网络不为一致。本地 my_test_network.json 中的节点结构、人设系数r以及话术库的固定倾向修正值等，仅仅是供选手在本地测试链路的示例数据，线上真实评测时，系统会使用为官方构建的隐藏宇宙种子

Q:有几个疑问帮忙确认下
1. 测试代码READM.md里说 “通信带宽限流（API Limits）：在单次图网络评测中，代码对大模型（LLM）的调用次数硬上限为 50 次（初赛标准）。” 真实运行环境是否存在该约束，且初赛复赛都是 50 ？
2. local_test.py中有 “while env.get_remaining_budget() >= 2.0 and step_count < 50:” 校验，不满足就结束游戏。(a)这里为什么不是budget > 0 . (b) 50 步的限制，这个真实运行环境也有吗，初赛复赛都一样吗？
A:
1.  local_test.py 和 README.md 中的50次（步数/调用llm限制）是早期内测版 SDK 的占位保护参数，选手测试时可根据自身配置的seed网络节点数，在SMP_Starter_Kit\custom_seeds\my_test_network.json调整"max_api_calls"来修改
 真实运行环境的llm调用限制是初赛120 次，复赛250 次。相应描述将同步更新在赛题描述中
2.（a）因为如果预算降到 【2 以下】，就只能执行侦察 scan，无法改变网络节点状态；（b）步数限制即调用llm限制，同上1解释

Q:
1. 赛题背景中写到 "从官方给定的话术库中选择预设策略", 这里的官方话术库每次共有几条，这个信息怎么获取。
2. 赛题背景中写到 得分计算会先经过 “3.推演结算， 4.单种子得分计算”，这里推演使用的网络共识算法是选手可知的吗，local_test.py 用注释跳过了这一步，直接进行了 第 4 步 trigger_eval。似乎离线测试感知不到 3 的作用
A:
1.有三个，其数值是对选手黑盒隐藏的，需要大模型根据节点反馈来选择
2.网络共识算法的宏观物理规则是公开的，即：节点连接度数越高，其观点保留能力与对邻居的影响力越大。但具体的数学演化过程由官方底层引擎托管；local_test.py 中的 env.trigger_eval()是在我们服务器上触发的3.推演结算

Q:是不是可以这样理解，这里的 3 和 4 指的是一件事，就是按照 4 中的说法“即所有存活节点稳态值与其度数权重的乘积之和” 进行计算，并没有其他中间过程了
A:不完全是，这里的3.推演结算说的是：在选手干预结束后，系统还会将此时的网络拓扑图，用网络共识算法进行动态迭代至稳态，然后才执行4
